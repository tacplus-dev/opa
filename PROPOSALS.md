- **Restrict the Rego built-ins policies may call** (2026-11-06, nightly scan): `NewPolicyEvaluator` (`internal/opa.go`) prepares every bundle with OPA's default capabilities. A pushed policy can therefore call `http.send` and the DNS built-ins, and from opa's pod at that. Those calls run on `context.Background()` (`Evaluate`), with no deadline, no cancellation and no `trace_id`. The proposal: pass `rego.Capabilities` with the network built-ins removed (or an explicit allowlist), and refuse a bundle that uses them at load. Why: an entitlement or proxy decision should be a pure function of its input. A policy that reaches out stalls kernel's login and proxy paths on a slow host, and its outbound calls would be the only downstream calls opa makes, untraced (tacplus-dev/looper#51). It's new behaviour, because a bundle that uses `http.send` today would be refused, so it needs a design and Jody's approval. Links: `decisions/security-audit-2026-09-12/CONSOLIDATED_REPORT.md` (Medium: "RPC context is discarded", which is a bug and separate, queued in `FIX-high-tier.md`), `raw-fable.md` §4.

- **The build's security checks miss standard-library vulnerabilities** (2026-11-11, nightly scan, #14): the checks run gitleaks, gosec and osv-scanner. osv-scanner reads go.mod, so a Go standard-library advisory (GO-2026-6859, net/http, fixed in Go 1.26.11/1.27.4) reaches opa's release unreported. Only the nightly scan's `govulncheck ./...` finds it. The proposal: the build's checks also run `govulncheck` in the pinned build image, so its Go toolchain is what's checked, and report stdlib findings like the others (tool, id, where, blocking). Why: the build image's Go version decides what ships, and a stale image (build:2.6.1 predates golang 1.27.4) is otherwise invisible to the policy. It's the build pipeline's behaviour, so it's tacplus-dev/looper's to design (README: Security checks; tacplus-dev/looper#49).
  Update 2026-11-15 (nightly scan): the build's checks now run govulncheck v1.9.0 (the 2026-11-15 report's "Checked against" lists it, db 2026-11-11), and its findings.json has no GO-2026-6859 while `tacplus.lock` still pins build:2.6.1 (#14 open). The looper README says govulncheck "loads a module with the Go it was built with" (1.27.4), so the standard library it checks is the scanner's, not the pinned build image's: the gap this proposal names is still open for stdlib advisories.
- **The nightly scan verifies the gates from the build's verdict, not by running `just gates` on its runner** (2026-11-15, nightly scan): the scan's checklist item 3 is "the repository's own gates failing on main (`just gates`)". On this scan's runner `just gates` cannot run: the `tacplus` wrapper runs the pinned `build:2.6.1` as a Docker container, and the runner has no Docker daemon (`/var/run/docker.sock` absent; `docker info` through the broker at `LOOPER_DOCKER_BROKER` fails the same way), so `tacplus build` fails before `go build`, `go vet` and `go test`, and `govulncheck ./...` cannot load the packages either (the generated `tacplus/` tree is missing). Only the gates' two pre-generation checks (no tracked `tacplus/` files, no upstream references) were verified today. The proposal: the scan reads the gates verdict of the repository's nightly build pipeline (tacplus-dev/build runs `gates` in the pinned image already, looper README "Security checks") and the generated tree the gates job keeps as its `built/` artifact, so item 3 and a source-mode `govulncheck` are verified where the build runs rather than re-run on a runner without Docker. Why: tacplus-dev/looper#84 removes Docker from every pod and #73 retires looper-docker, so re-running the gates on the scan runner stops being possible by design; without a verdict to read, item 3 is silently unverifiable and the scan cannot tell a broken main from a runner without Docker. It's the scan's behaviour, so tacplus-dev/looper's to design (looper#84, looper#73, looper#17).
  Update 2026-11-15 (nightly scan, later run): the gates were verified on main (5398d84) another way. The pinned release binary the `tacplus` wrapper caches and checksum-verifies (`$LOOPER_TACPLUS_HOME/.cache/tacplus/2.6.1/tacplus`, a static arm64 binary) runs natively on the runner, which has `protoc`: in a scratch clone, `tacplus build --tag latest` with `GH_TOKEN` from `gh auth token` generated `tacplus/` and changed no tracked file, then `CGO_ENABLED=0 go build -trimpath`, `go vet ./...` and `go test ./...` passed, and with the generated tree present `govulncheck ./...` (source mode: no reachable vulnerability, GO-2026-5932 required but not called) and `looper-trace check` (0 handlers, 0 findings) ran too. The caveat: the Go is the runner's (1.26.11), not the pinned image's (1.27), so this verifies the code, not the release toolchain (#14). Until the build's verdict is readable, the scan could run the gates this way (run the cached binary directly when Docker is absent) instead of failing at `tacplus build`.
